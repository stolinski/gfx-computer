# Multi-state composition — transition Effects sample two states sharing one frame

## Status

**Superseded by [ADR-0068](0068-films-scenes-and-live-scene-boundaries.md) phase 2 on 2026-10-09.** A transition is now a **Scene boundary** between two Scenes of a Film, live on both sides, which is the "render both states live" this record first asked for, done by swapping one engine state per frame. The two-endpoint `transition` Preset form decided here is no longer written or drawn as such: it is accepted on read and lifted to a two-Scene Film with one boundary (ADR-0068 §3). The text below is the record of the original decision.

**Was: Canon model; implementation refined by ADR-0026.**

> **Status — Model canon, implementation refined by [ADR-0026](0026-transitions-v1-snapshot-and-wipe.md).** The composition *model* and *schema* pinned here stand: a Preset declares `transition: { from, to, effect, durationMs }`, `from`/`to` are full normal Presets referenced by slug, and a transition Effect composites them with per-pixel selection (not a crossfade). The **"render both states live into two target pairs every frame"** implementation decision below is **revised by ADR-0026** — it fights the engine's global-singleton + live-DOM architecture; v1 instead snapshots each state once into a cached texture and animates the wipe mask over the two static textures. The live dual-tree render is the documented upgrade path, not the v1 build. Tracked in [`../roadmap.md`](../roadmap.md).

A transition Effect like `mask-wipe` (animated reveal from a starting composition into an ending composition, masked by a procedurally-shaped boundary) cannot be expressed under the engine's single-composition-per-frame model. The engine renders one composition tree per frame; an Effect runs as a post-process pass over that single composition's color target. A wipe between two compositions needs *two* color targets sampled by the same fragment — the wipe's mask shape selects "this pixel comes from state A, this pixel comes from state B" — and the engine has no scheduling primitive for "render state A and state B in the same frame and hand both to the Effect." Today an author can fake a wipe by stacking two Surfaces and animating the upper one's opacity, but the result is a crossfade (the two contributions composite into a single color target before the wipe runs), not a wipe (the wipe shape never gets to choose which contribution wins per pixel — by the time it runs, the answer is already a blended mid-pixel). The motion-primitives plan paused on this in Phase 3.2 to pin the composition model before any transition Effect ships. We pin three decisions. First, a transition is a Preset shape: a Preset's top-level may declare a `transition` block with `from: <PresetRef>`, `to: <PresetRef>`, and an `effect` field naming the transition Effect Pipeline. The `from` and `to` Presets are full normal Presets in their own right; the transition Preset references them by slug. Second, the engine schedules both per frame: when a Preset declares a transition, the renderer runs the full composition tree of `from` into one color+depth target pair, runs the full composition tree of `to` into a second color+depth target pair, and hands both target pairs to the transition Effect as bound input textures. Third, the transition Effect's shader samples both color targets per pixel and chooses (or blends) according to its mask shape evaluated at `progress`. The mask shape is the Effect's whole job; the engine just guarantees both states are available.

## Considered options

Per-Preset state pair declared inline (`states: [stateA, stateB]` with the rest of the Preset body shared) (rejected: forces both states to share the same top-level shape — same Surface, same Body slots, same Overlays — which excludes the most useful wipe case: wipe between two *different* Surfaces — and re-introduces the bundling ADR-0014 was built to remove because both states now share aesthetics by file structure). Single-state Preset with the transition expressed as a per-element animation timing override (rejected: collapses to a crossfade for the reasons named above — no mask-shape primitive can resolve a pixel between two contributions that have already been alpha-blended, and the "wipe" name lies about what the renderer actually does). Render `from` and `to` to off-screen targets in advance via a build-time pre-render step (rejected: build-time targets cannot animate, and the v1 use case includes wipes whose underlying contributions are themselves animated — a Body counter ticking over while a wipe reveals it — which requires per-frame re-evaluation of both states, not a pre-rendered snapshot). External transition Pipeline that owns its own pair of inner-Preset declarations as a nested schema (rejected: works mechanically but couples the schema to a specific transition family; we want the transition Preset to be a thin recipe that names two existing Presets and an Effect, which is the same shape Briefs and brainstorm already use to reference Presets).

## Consequences

The Preset schema gains an optional top-level `transition` field of shape `{ from: PresetSlug; to: PresetSlug; effect: TransitionEffectRef; durationMs: number }`. When present, the engine's render path forks: the composition tree resolution function runs once for `from` and once for `to`, each writing into its own (color, depth) target pair. The Effect chain for the transition Preset runs after both forks complete and binds the two target pairs as input textures; the transition Effect's shader samples both, evaluates its mask shape at the current `progress`, and writes the composited output to the frame's final color target. Transition Effects are a distinct registry lane from the existing per-Layer Effect Pipelines — their fragment shader's input shape is different (two color textures and two depth textures rather than one of each) and the engine refuses to wire them as ordinary post-process Effects. The transparency contract holds: both states are alpha-composited as usual into their respective targets before the transition Effect runs; the transition Effect's output preserves alpha; the export sees a single transparent WebM with the wipe encoded in the alpha + color channels frame-to-frame. The `progress` value passed to the transition Effect is the wipe's local progress (0 = fully `from`, 1 = fully `to`), distinct from the global `progress` value that drives `from`'s and `to`'s own animations. The engine work (the dual-tree render pass, the transition Effect registry lane, the two-target-pair binding plumbing) is deferred to a separate Brief alongside `mask-wipe`; only the composition model pins in this ADR. The motion-primitives v1 library does not ship `mask-wipe` for the same deferral reason — the plan explicitly pulls it out of v1 scope. ADR-0021's depth-as-sidecar model carries through unchanged: both target pairs include their own depth target, which means a transition Effect that wants to read depth (e.g. a wipe whose softness varies by focal distance) has the input available without further engine changes once the plumbing lands.
