# Transitions v1 — snapshot-and-wipe, not live dual-tree render

## Status

**Superseded by [ADR-0068](0068-films-scenes-and-live-scene-boundaries.md) phase 2 on 2026-10-09.** The frozen endpoints decided here are retired: a Scene boundary renders both of its Scenes live on every frame of its window, and the snapshot controller, `transitionState`, and the frame renderer's prepared-transition branch are deleted. What survives is the transition effect registry and its two-view pass contract, which a boundary drives. A Preset that states `transition` is still read, as a two-Scene Film with one boundary. The text below is the record of the v1 decision.

**Was: Canon (v1 built). Refines [ADR-0022](0022-multi-state-composition.md).** The composition _model_ and _schema_ from ADR-0022 stand unchanged: a Preset declares `transition: { from, to, effect, durationMs }`, the `from`/`to` Presets are full normal Presets referenced by slug, and a transition Effect composites them. What this ADR revises is **how** the two states reach the transition Effect: not a per-frame live dual-tree render, but a one-time snapshot of each state into a cached texture that the transition Effect animates a mask over.

**Implementation note (2026-07-23).** Preview, settled-state snapshot capture, and export target `renderCompositionFrameTo(request)` in `composition-frame-renderer.ts`; `Workspace.svelte` owns the live dependencies and builds each request. A prepared wipe has first precedence and does not upload irrelevant live DOM; snapshot capture runs through the seam's live branch while the wipe is unarmed. Export therefore renders the prepared transition rather than rebuilding a separate flat/stage/DOF dispatch. Output classification marks the transition opaque only when both resolved endpoint Presets are opaque.

ADR-0022 pinned that the engine renders the full composition tree of `from` and of `to` **into two target pairs every frame**, so a transition Effect can mask between two _animating_ states. That decision does not survive contact with the engine's architecture. Supers renders via WICG HTML-in-Canvas: a composition is not a data structure the engine draws imperatively, it is a **live DOM subtree** that `copyElementImageToTexture` rasterizes, and every Pipeline that renders it reads the **global `$state` singletons** (`engineState`, `animState`, `packState` — `OverlayMount` imports them by module, not by prop). Rendering two _different_ Presets live in the same frame therefore requires either two simultaneous live DOM subtrees driven by two coexisting engine-states — which the singleton architecture cannot hold without threading scoped state as props through every component that currently reads the global — or running two of everything against a singleton that only ever holds one state. Both fight the engine at every level; the second is the kind of brittle co-rendering that the project's render path has already paid for once.

We choose the model every non-linear editor uses instead: **snapshot, don't co-render.** When a transition Preset loads, the engine renders `from` once through the existing single-composition path and captures the composited frame into a cached colour texture, then renders `to` and captures a second texture. The transition Effect (`mask-wipe` first) then runs every frame over those **two static textures**, animating only its mask shape at the wipe's local `progress` (0 = `from`, 1 = `to`). The wipe's per-pixel selection — the whole reason ADR-0022 rejected a crossfade — is preserved: the mask still chooses "this pixel is `from`, this pixel is `to`," it just chooses between two settled images rather than two live trees. The two setup captures swap the global engine-state twice and let Svelte flush the DOM between them (a handful of frames at load), not twice per frame.

## Considered options

- **Live dual-tree render every frame (ADR-0022 as written)** (rejected for v1): mask between two _animating_ states, but requires two coexisting live DOM subtrees + two engine-states against a singleton architecture — high-risk co-rendering for a capability (a state animating _during_ the wipe) that bumper wipes almost never need.
- **Per-frame global-state swap + double capture** (rejected): keep one DOM, but each frame set the global state to `from`, render+capture, set it to `to`, render+capture, then mask. Animating states without two subtrees — but it relies on the DOM reflecting each swapped state _synchronously twice per frame_, and Svelte DOM updates flush async; the export path already wrestles with sync DOM capture. Same brittleness, condensed into the hot loop.
- **Context-scoped engine-state refactor** (rejected for v1, kept as the eventual upgrade path): make components read their composition's state via Svelte context instead of the module singleton, so two `Composition` instances can each carry their own state cleanly. This is the _correct_ long-term fix and the path to genuine live dual-tree, but it touches every singleton consumer — too large to fold into v1, and not needed until a Preset actually requires mid-wipe animation.
- **Snapshot-and-wipe** (chosen): reuses the single-composition render path unchanged, adds only "render a Preset to a cached texture" (the effect chain already renders to intermediate textures) and a two-input transition Effect. Robust because it stops fighting the singleton + live-DOM model.

## Consequences

The shipped transition Effect lane binds **two colour snapshots + a local wipe `progress`** — not the two colour + two depth pairs ADR-0022 originally described. Flat and dimensional depth rendering have since shipped, but transition snapshots intentionally remain colour-only; a future depth-sensitive wipe may extend the lane without changing authored transition Presets. Each endpoint is captured at a **settled representative frame** so the wipe transitions between two finished images. The transparency contract holds end to end: each snapshot is a premultiplied-alpha composite and `mask-wipe` preserves alpha. The traded capability remains `from`/`to` continuing to animate during the wipe; a genuine need for that behavior would trigger the context-scoped live dual-tree upgrade described above.
