# GFX Agent Instructions

GFX is an opinionated, high-end **motion-graphics engine** on a web stack (TypeGPU/WebGPU + WICG HTML-in-Canvas + GSAP + Mediabunny). It produces broadcast-quality motion pieces — **transparent overlays** composited over footage, and **full-frame segments/bumpers** — authored by a GUI and by agents over one composition model. Schema, persistence, create-from-blank, standalone interchange, GUI validation and verification, shared agent store access, and deterministic automated rendering are all shipped ([ADR-0032](docs/adr/0032-gui-agent-parity-authoring.md), operational workflows in [`docs/user-composition-workflows.md`](docs/user-composition-workflows.md)); a browser agent authors the same composition through WebMCP ([ADR-0054](docs/adr/0054-webmcp-operation-transaction-and-security-contract.md)). Compositions are JSON **Presets** that compose five Layers (Surface / Block / Annotation / Overlay / Effect) from a Pipeline registry; **appearance** is supplied by a swappable **Pack** (the engine is general, the look is not); pieces **reflow** across horizontal (YouTube) and vertical (TikTok/Reels) targets with platform safe-areas. The quality bar is Netflix-grade: _After Effects is the quality ceiling, not the architecture_ — GFX stays a tasteful, constrained vocabulary with smart defaults, never a general node compositor. Glossary: [`docs/CONTEXT.md`](docs/CONTEXT.md). Why per-tool routes became one engine: [ADR-0002](docs/adr/0002-per-tool-routes-to-preset-engine.md).

> `CLAUDE.md` is a symlink to this file — this is the single canonical entry point for every agent tool.

## Binding rules — apply to every task

- **Transparency is the default, not a law.** Overlays render transparent — `loadOp: 'clear'`, `clearValue: [0, 0, 0, 0]`, canvas context `alphaMode: 'premultiplied'`. A composition **may** declare a background fill, which makes it a full-frame piece (segment/bumper); output classification changes the filename and WebM pixel format, while the current ProRes lane remains 4444 for both transparent and opaque compositions. Never paint a background a composition didn't ask for.
- **Frame-determinism.** Drive all animation from an explicit `timestamp` / `frame` value. Scrub paused GSAP timelines by `progress`; never play by wall-clock. Preview and export must produce the same pixels at the same time.
- **Native target resolution.** 3840×2160 horizontal or 2160×3840 vertical. No upscaling from a smaller intermediate.
- **Every deliverable Preset ships both orientations, each art-directed, and is Pack-neutral.** One Preset carries a horizontal and a vertical composition, and each must look good on its own terms; neither is expected to fall out of the other automatically. The engine's job is to give GUI and agent authors the tools to compose each orientation directly — complete per-orientation placement and motion for every element ([ADR-0039](docs/adr/0039-pack-neutral-compositions-and-listing-hygiene.md) §4, amended 2026-09-23). When an orientation cannot be made to look good with the tools that exist, that is an engine gap to fix, not a layout to settle for and not a reason to ship a second file. The Pack rule is unchanged: the same Preset must look good under every Pack. Never create per-orientation or per-Pack variants of a composition, and never ask whether a preset "should support" vertical or horizontal — _how_ each orientation is composed is designable; _whether_ it ships both is not. Existing fixture-only recompositions and Pack calibration re-dresses document engine gaps or validate Packs; they are not listed deliverables or authoring precedent.
- **Strict TypeScript.** No `any`. `unknown` at trust boundaries, narrowed before use. Explicit return types on exports. No re-exports — import from source.
- **Critic is advisory.** The Critic is an optional adversarial observation tool (see [`docs/critic.md`](docs/critic.md)); its prose has no approval, rejection, or routing authority. Deterministic checks (`pnpm check`, `pnpm test`, `pnpm verify-presets`) decide pass/fail; human aesthetic approval is the only subjective acceptance authority.
- **Direct delivery is the default; factory delivery is opt-in.** Work directly with the user in a linked worktree unless the user explicitly requests `gfx-factory` for unattended, queued, or batch delivery of Dex tasks. The factory is never a prerequisite for implementation, verification, review, or integration. Keep `gfx-factory` available as an automation lane and `sentry-autofix` as the automated Sentry repair lane; keep both definitions small, with behavior in stage YAML and prompts rather than new extension code.
- **Completion requirements do not depend on the delivery path.** Direct and factory-assisted changes must both update affected documentation and planning surfaces in the same change, keep any corresponding Dex state in sync, run the relevant deterministic checks, obtain human aesthetic review for visual changes, and rebuild + smoke the production service after integration. Use existing automation such as `gfx-verify.run_checks`, `pnpm audit:planning`, `pnpm check`, `pnpm test`, `pnpm verify-presets`, and `gfx-verify.rebuild_and_smoke` when applicable. A change is not complete while its governing docs or acceptance evidence are stale.
- **Implementation work uses a linked Git worktree.** Before the first repository mutation, determine whether the current checkout is the primary checkout. If it is, create a linked worktree from the current exact `HEAD` and perform all implementation reads, edits, commands, and commits there. If already in a linked worktree, continue there. Never copy implementation files into the primary checkout for testing. The primary checkout is reserved for serialized integration and post-integration verification. Its unrelated dirty state is never an implementation, feature, planning, or Sentry admission failure. Use any available standard Git or agent worktree mechanism; Herdr is not required.
- **Svelte runes discipline.** No `$effect` unless genuinely necessary. No rename-only `$derived` aliases. Components own their own data — read from managers / route directly where used; no prop-forwarding wrappers.
- **UI restraint.** No refresh buttons, save buttons, or explanatory text. Less UI > more UI. Use the simplest, flattest semantic HTML. Graffiti tokens and patterns before custom CSS.
- **Never run destructive git** (`git reset --hard`, `git revert`, `git restore`, `git clean -f`, force-push) without explicit user permission.
- **Two serving URLs — never start your own server on their ports, never point either at Vite.** `https://gfx.robo.online` serves the **production build of `main`**: `node build/index.js` on port 7263, supervised through `local-dev-control` and rebuilt + restarted after every integration by `gfx-verify.rebuild_and_smoke`, whether delivery was direct or factory-assisted. That method also smoke-checks status, `/api/health`, and the `gfx-release` meta against the landed commit. `https://gfx-review.robo.online` (port 4173) presents pending work for human judgment. There is no dev domain: run Vite HMR ad hoc on a bare localhost port when you need it, and keep every verification serve jailed worktree-local with its own store and ports. **These two URLs are the entire browser-facing surface, managed only through the swamp `local-dev-control` system (the `local-dev` skill): app work for human judgment goes on `gfx-review`, and `gfx` picks up the prod build of `main` after integration.** Never `tailscale serve`, `tailscale funnel`, or any other ad-hoc tunnel — bare `tailscale serve --bg <port>` claims HTTPS 443 for the whole tailnet, silently shadowing Caddy and downing every robo.online domain for every device while health checks on this machine stay green. The inverse holds too: do not provision new local-dev domains or push scratch files, artifacts, or probe output onto the local-dev system — anything that isn't one of those two deliverable surfaces stays on bare localhost or on disk.
- **GFX is local-first; its production target is a Node origin you serve yourself, and gfx.computer is a hosted origin that encodes nothing.** Work runs on the local dev server. The production artifact is one Node/ffmpeg origin, built and served on loopback under the `public` runtime profile ([`docs/production-serve-rollback-runbook.md`](docs/production-serve-rollback-runbook.md)), and server routes freely use Node APIs, the local filesystem, and local binaries — never treat Workers/edge constraints as binding on the engine, and never pick a library or architecture "for Cloudflare compatibility." Since 2026-09-02 ([ADR-0052](docs/adr/0052-public-runtime-and-retention-architecture.md) amendment) the same app is also deployed to `https://gfx.computer` as one Cloudflare Worker under the `hosted` profile, declared by `PUBLIC_GFX_HOSTED`: the browser renders and encodes every export there (WebM only, `browser-webm-export.ts`), the export transport and every development-only route answer 404, and the origin keeps nothing — no KV, D1, R2, or Durable Objects, ever. Hosted-mode differences go through the existing inventories (`public-surface-inventory.ts`, `composition-export-formats.ts`, `IS_HOSTED_ORIGIN`), never through scattered conditionals; a Node-only import in the server tree needs a hosted stand-in in `vite.config.ts`, not a rewrite. The docs site (`docs-site/`) lives at `https://docs.gfx.computer`, never the apex. Operations: [`docs/hosted-origin-runbook.md`](docs/hosted-origin-runbook.md). Both non-development profiles are narrower than what you develop against: a **Public demo session** is browser-scoped, with no accounts, no server-side composition store, and no durable visitor content, so the disk-backed User composition, asset, and poster surfaces are development-only ([ADR-0053](docs/adr/0053-gfx-namespace-and-legacy-supers-compatibility.md)). Developing against those local surfaces is never permission to persist a visitor's work under the `public` or `hosted` profile.
- **Temporary, while the WebMCP Challenge runs (added 2026-09-03; remove when it ends): work pushes to the `dev` branch, never to `main`.** The primary checkout sits on `dev` for the duration, and every rule in this file that names `main` reads `dev`: worktrees branch from it, integration fast-forwards into it, `gfx.robo.online` rebuilds from it, and pushes go to `origin/dev`. `main` is frozen at the state the challenge started from (dimensional type landed) and is not pushed again until the challenge ends, when `dev` fast-forwards into `main` and this rule is removed.
- **GFX is the current namespace; Legacy Supers names are classified, never bulk-replaced.** The product is GFX and its reserved domain is gfx.computer; identifiers spell it `gfx` and environment variables use `GFX_`. Every remaining `supers` occurrence carries exactly one disposition from [ADR-0053](docs/adr/0053-gfx-namespace-and-legacy-supers-compatibility.md) — `current`, `rename-now`, `accept-old / write-new`, `deprecated alias`, `frozen`, or `historical` — and renaming a value the matrix does not list means adding its row, not guessing. Legacy readers ship before GFX writers. `pnpm check:names` enforces this: a legacy spelling is a defect unless `scripts/check-legacy-name-dispositions.mjs` declares the surface it belongs to, so adding a legacy surface means adding both its ADR row and its declared-surface row. Never run a tree-wide find-and-replace, and never rewrite history (ADRs, `docs/history/`, `.dex/`, git).
- **Agent authoring is an Operation, never a UI gesture or a raw patch.** Every authoring capability is one row in the **operation inventory** (`src/lib/platform/webmcp-operation-inventory.ts`), owned by exactly one of the fifteen operation families, and reachable from both the GUI and a WebMCP tool ([ADR-0054](docs/adr/0054-webmcp-operation-transaction-and-security-contract.md)). Mutating operations take the caller's observed **Composition revision**, apply atomically or not at all, record one shared undo entry, move the visible Workspace focus, and return a bounded **Operation receipt**. Never add a tool that clicks, scrolls, opens a panel, patches a JSON pointer, or writes engine state directly; never register a tool that cannot succeed in the current state; derive every enum from the live registries rather than restating it. Adding a capability means adding its inventory row.
- **Canvas-verification Chrome is already solved — never improvise a launch.** Rendering needs `--enable-blink-features=CanvasDrawElement`; a browser without it is hard-gated — the app shows a full-screen notice with the launch command instead of any approximate composition (no DOM-rasterization fallback is reachable), though WebMCP tools still register behind that notice, so a headless WebMCP browser authors without the flag and only the operations that render need it. **The default local agent mode is the combined-flag browser: `CDP_BROWSER_MODE=agent scripts/launch-cdp-chrome.sh` (CDP 9229, `--enable-blink-features=CanvasDrawElement,WebMCP`)** — WebMCP tools drive the real renderer in one browser. All render **validation and verification passes are deterministic scripts driving the CDP harness** — start/confirm the harness with `scripts/launch-cdp-chrome.sh` (modes: canvas 9223, agent 9229, standard-webmcp 9225, standard 9227) and drive it with the scripted runners only: `scripts/cdp-*.mjs`, `scripts/run-gfx-render-matrix.mjs`, `scripts/run-gfx-layout-contract-matrix.mjs`, and the `scripts/probe-*` family. Never drive a verification or matrix pass through the `chrome-devtools` MCP browser or any interactive MCP tooling — the MCP browser (configured in `~/.claude.json`, flag included) exists solely for interactive human-facing inspection of a live page. A sweep that is not reproducible as one script invocation is not verification evidence.
- **Utilities live in `src/lib/utils/`.** No new utility folders. Extend existing helpers before adding new ones.
- **No TODOs, placeholders, or no-op stubs.** Wire it now or the task isn't done.
- **Plain language.** Always respond to the user using the plain-language principles in ISO 24495-1:2023.

## Agent discoverability

- **Write names for search.** Exported symbols, methods, domain types, files, and directories must be distinctive search terms. Prefer two or three descriptive words including a domain noun (`createStripeClient`, `PresetRenderResult`) over generic names (`create`, `Client`, `Result`, `Data`, `Config`).
- **Use one spelling per concept.** Follow the canonical terminology in `docs/CONTEXT.md`; do not mix aliases or abbreviations such as `organizationId` / `orgId`, or rename imports without a concrete conflict.
- **Keep modules concept-focused.** Prefer domain-named files over generic grab bags. Split large mixed-concern modules when the resulting files can be named after coherent concepts; do not split solely to satisfy a line-count target.
- **Make types searchable and corrective.** Use precise domain types instead of primitive-shaped parameters where values can be confused. Prefer distinct ID types when swapping IDs would otherwise type-check.
- **Document where search lands.** Put short comments about non-obvious constraints or intent directly above the relevant definition. Document intentional absences where a reader would reasonably search for the behavior.
- **Pair source and test names.** Name colocated tests after the source unit they cover (`preset.ts` -> `preset.test.ts`) so implementations and verification are found together.
- **Identify legacy code.** Remove obsolete paths when possible; otherwise mark retained APIs with `@deprecated` and name the supported replacement.

## Repo layout

- `src/routes/` — SvelteKit routes. Presets render through a unified shell, not per-tool routes.
- `src/lib/platform/` — engine shell: `Workspace`, `Composition`, mounts and inspectors; `composition-frame-renderer.ts`, `composition-export-controller.ts`, and `transition-snapshot-controller.ts` own their named orchestration; `timeline-entity-identity.ts` owns runtime timeline identities; `user-composition-store.ts` owns the client-side User composition transport; plus state, schema, preset, GPU, HTML-in-Canvas, audit, lint, and encoding modules.
- `src/lib/pipelines/<layer>/` — the per-Layer **Pipeline** renderers (`surfaces/`, `blocks/`, `annotations/`, `overlays/`, `effects/`), one folder per variant.
- `src/lib/platform/pipelines/` — Registry + runner **infrastructure** only (`definition-registry.ts`, `runtime-loader.ts`, `identity-registry.ts`, `effect-chain.ts`, `shader-pass-runner.ts`, `types.ts`) — not the renderers.
- `src/lib/annotations/` — annotation-mark geometry and 2D drawing shared across Annotation Pipelines.
- `src/lib/presets/` — the built-in **Presets** as JSON.
- `src/lib/utils/` — the only utility folder. Don't create new ones.
- `scripts/` — verification and probe scripts (`scripts/probe-*.ts` for Critic measurements).
- `docs/` — reference docs dispatched from this file.

# Project

This repository is managed with [swamp](https://github.com/swamp-club/swamp).

## Rules

1. **Search before you build.** When automating AWS, APIs, or any external service: (a) search community extensions with `swamp extension search <query>` — prefer `@swamp/*` official extensions first, (b) search local/installed types with `swamp model type search <query>`, (c) if a community extension exists, install it with `swamp extension pull <package>` instead of building from scratch, (d) extend an existing type if it covers the domain but lacks the method you need, (e) only create a custom extension model in `extensions/models/` as a last resort. Use the `swamp` skill for guidance. The `command/shell` model is ONLY for ad-hoc one-off shell commands, NEVER for wrapping CLI tools or building integrations.
2. **Extend, don't be clever.** When a model covers the domain but lacks the method you need, extend it with `export const extension` — don't bypass it with shell scripts, CLI tools, or multi-step hacks. One method, one purpose. Use `swamp model type describe <type> --json` to check available methods.
3. **Use the data model.** Once data exists in a model (via `lookup`, `start`, `sync`, etc.), reference it with CEL expressions. Don't re-fetch data that's already available.
4. **CEL expressions everywhere.** Wire models together with CEL expressions. Always prefer `data.latest("<name>", "<dataName>").attributes.<field>` over the deprecated `model.<name>.resource.<spec>.<instance>.attributes.<field>` pattern.
5. **Verify before destructive operations.** Always `swamp model get <name> --json` and verify resource IDs before running delete/stop/destroy methods.
6. **Prefer fan-out methods over loops.** When operating on multiple targets, use a single method that handles all targets internally (factory pattern) rather than looping N separate `swamp model method run` calls against the same model. Multiple parallel calls against the same model contend on the per-model lock, causing timeouts. A single fan-out method acquires the lock once and produces all outputs in one execution. Check `swamp model type describe` for methods that accept filters or produce multiple outputs.
7. **Extension npm deps are bundled, not lockfile-tracked.** Swamp's bundler inlines all npm packages (except zod) into extension bundles at bundle time. `deno.lock` and `package.json` do NOT cover extension model dependencies — this is by design. Always pin explicit versions in `npm:` import specifiers (e.g., `npm:lodash-es@4.17.21`).
8. **Reports for reusable data pipelines.** When the task involves building a repeatable pipeline to transform, aggregate, or analyze model output (security reports, cost analysis, compliance checks, summaries), create a report extension. Use the `swamp` skill for guidance.
9. **"Workflow" means a swamp workflow.** In this repository the word "workflow" (and "create/run/execute/validate/debug workflow", "automate", "orchestrate", "automated/nightly job") refers to a swamp workflow — a declarative YAML DAG of model-method steps authored via `swamp workflow create`. Load and follow the `swamp` skill for these requests. Do NOT interpret these as a request to build an agent task list, spin up worktrees, or schedule a cron/remote agent. Only use those orchestration mechanisms when the user explicitly names one (e.g. "task list", "subagent", "worktree", "cron", "remote agent") or explicitly asks you to do the work yourself step by step rather than author a swamp workflow.
10. **Use swamp, don't bypass it.** Always work through swamp commands — don't go around them with raw shell tools. Use `swamp data query` to find data, not `grep`/`find` on `.swamp/` files. Use model methods to interact with resources, not `curl`/`aws`/`gcloud`/`kubectl` when a model type already wraps that API — check with `swamp model type search`. Use `swamp help` for CLI discovery, not guesswork. Composing with swamp output is fine (e.g. piping `--json` through `jq`) — the anti-pattern is bypassing swamp entirely.
11. **Inspect reports after failures.** When a model method or workflow run fails, inspect its generated reports before retrying or changing definitions. Reports run even on failure and capture structured diagnostics — error messages, execution status, arguments, and data output pointers. Use `swamp report get @swamp/method-summary --model <model> --json` for method failures or `swamp report get @swamp/workflow-summary --workflow <workflow> --json` for workflow failures. Run `swamp help report get` to confirm current retrieval syntax.
